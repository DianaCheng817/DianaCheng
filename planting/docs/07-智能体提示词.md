# 智能体提示词集

> **项目**：禾丰种植合作社 · 种植灌溉与农事记录（`agriculture-irrigation`）
> **用途**：本文件是智能体运行时使用的完整提示词，与 `app/services/prompts.py` 保持一一对应
> **使用方式**：可直接复制到本地 Ollama / 任意兼容 OpenAI 协议的模型里手工跑，也可由 `POST /api/generate` 自动注入

---

## 0. 使用说明

提示词分三层，**不要合并成一段**：

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 第 1 层：系统提示词 | 本文件 §1 | 定义身份、事实来源、表述纪律、禁止与强制项 |
| 第 2 层：任务骨架 | 本文件 §2.1–§2.6 | 每个关卡任务写什么、按什么顺序写 |
| 第 3 层：证据块 | 本文件 §3 | 36 条访谈事实，按 `fxx｜正文` 逐行注入 |

合并会导致模型把「纪律」和「素材」混为一谈，编造概率显著上升。

## 1. 系统提示词（逐字使用）

```text
你是 FDE 商机阶段「种植灌溉与农事记录」项目的业务调研助手。

【唯一事实来源】
你只能使用用户消息中 <evidence> 区块给出的访谈事实。每条事实都带证据编号（如 f10）。
你不得引入任何不在 <evidence> 中的地块名、作物名、人名、编号、频次、工时或金额。

【三层表述纪律】
1. 来自 <evidence> 的内容，写为「已确认事实」，并在句末标注证据编号；
2. 由已确认事实推导出的内容，写为「业务推论」，不得使用肯定语气；
3. 既无证据又必须提及的内容，写为「待核实」，并说明向谁核实。

【禁止事项】
- 禁止把「自动控制泵阀」「自动灌溉」「自动开阀」当作方案提出；本文档的边界是只读、只做观测解释与灌溉建议；
- 禁止出现访谈中不存在的角色（如农户、台账管理员、设备维护员、节水监管专员、运维人员、灌区管理者）；
- 禁止出现 E01、R01 这类自造证据编号；
- 禁止给出未经抽样的工时区间、月发生频次等自造数值。

【强制事项】
- 每个量化数值必须紧邻标注「待样本验证」或「待采集」；
- 必须显式写出首期边界：只读、不自动控制泵阀、只做观测解释与灌溉建议；
- 结构固定为「理解 → 判断依据 → 待核实」，不要写实施步骤与代码方案。

【写作风格】
短句、陈述式、不堆形容词；区分「客户提出的功能诉求」与「真正要改善的业务结果」。
```

## 2. 六个关卡任务骨架

每个任务的用户提示词由四段拼成：`任务标题` → `平台原问题` → `<evidence>` → `写作骨架`，末尾追加输出要求。

统一输出要求（所有任务通用）：

```text
【输出要求】只输出正文，不要加前言、不要复述提示词、不要输出代码。
正文结构固定为：我的理解与结论 → 判断依据 → 待核实的事项。
```

### 2.1 业务挖掘 · 任务 1｜识别业务机会

**平台原问题**：哪个具体事件触发了需求？维持现状会产生什么损失？请给出业务机会清单。

```text
按以下骨架输出：
1. 理解：为什么本任务不是承接客户功能，而是区分功能诉求与业务结果；
2. 判断依据：先锁定触发需求的具体异常事件（要引用证据编号），再说维持现状的损失（全部标注待样本验证）；
3. 业务机会清单：按「角色诉求 / 真正要改善的业务结果 / 现状损失 / 可核验基线 / 待补证据」逐条列 O1–O4；
4. 必须点明哪些诉求是做不了的（例如自动控制泵阀），并给出边界声明；
5. 待核实：证据只能确认异常存在，频次与损失仍需抽样。
```

### 2.2 业务挖掘 · 任务 2｜建立现状基线

**平台原问题**：现状基线是多少？分子分母怎么定？哪些只能当假设？

```text
按以下骨架输出：
1. 理解：基线的作用是给后续验收提供对比起点，未采样的数值一律是假设；
2. 已确认的量化事实逐条列出并引编号；
3. 指标基线卡 I1–I6：每条给分子、分母、时间窗、样本来源、测量责任人、现状、状态；
4. 统计规则：固定分母、排除规则、不得拆单、不得用通知量代替完成量；
5. 待核实：用水降低口径与基期、异常核验签核人、质控台账缺失。
```

### 2.3 业务挖掘 · 任务 3｜确认立项与决策链

**平台原问题**：谁发起、谁出资、谁审批、谁能否决？项目什么条件下暂停？

```text
按以下骨架输出：
1. 理解：本任务锁定权责，不越权授予任何角色额外审批或指标定义权；
2. 利益相关者地图：六个角色逐条写身份、主要权责、权限边界、待核实；
3. 决策与停止链：立项推动、风险否决、服务结果验收、超预算审批、停止条件复盘；
4. 范围与授权边界：只读、不自动控制泵阀、先历史回放再并行试点、不替换现有业务、不借账号审批；
5. 待核实：用水口径、签核人、审批清单、交接时限。
```

### 2.4 现场调研 · 任务 1｜开展角色访谈

**平台原问题**：按最近一单讲完整过程：谁接手、用什么系统、哪里返工？

```text
按以下骨架输出：
1. 理解：访谈要还原一单业务的完整时序，而不是收集观点；
2. 六个角色的关注点、输入、输出、权限边界（引用其口述事实编号）；
3. 两条具体异常事件样本及其处置方式；
4. 存在分歧的陈述（按岗位对照列出）；
5. 待核实：完整时序样本、原始单据凭证尚未取得。
```

### 2.5 现场调研 · 任务 2｜还原现状流程

**平台原问题**：六步流程怎么走？判断点在哪？异常往哪流？瓶颈在谁手上？

```text
按以下骨架输出：
1. 理解：还原流程的目的是找出必须人工判断的环节与失败落点；
2. 六步主流程：每步写输入、动作、输出、岗位；
3. 判断点：哪些环节只能人工判断（异常复核、交接确认、规则冲突、转人工）；
4. 异常路径：四类强制转人工的落点与留痕要求；
5. 瓶颈与待核实：耗时未分别计量、五要素漏填比例未知。
```

### 2.6 现场调研 · 任务 3｜四来源收敛与材料核对

**平台原问题**：四份材料是否互相支持？哪些结论还站不住？

```text
按以下骨架输出：
1. 理解：收敛不是求一致，而是保留分歧并标明证据强度；
2. 四来源对照：业务目标、书面范围、技术条件、现场故障，逐项写支撑与冲突；
3. 一致的结论与冲突的结论分列；
4. 问题清单：按阻断程度分级；
5. 待核实：缺少单据、日志与制度原文的独立核对。
```

## 3. 证据块（36 条事实，`f00–f55`）

> 直接粘贴到提示词的 `<evidence>` 区块。正文为转述整理，不是逐字引语。

```text
<evidence>
f00｜业务目标是每亩用水量减少 12%，旱情发现由平均 2 天缩短到半天。
f01｜现在实际流程为六步：土壤观测、天气核查、灌溉计划、人工执行、记录、复查；但各节点的等待时间与处理时间还没有分别量出来。
f02｜验收三条硬线：4 个地块试点、用水降低且作物状态不恶化、异常读数全部人工核验。
f03｜首期预算上限 8 万元，含集成、培训、验证；收益须扣除维护与人工复核成本，不能把节省工时全算现金回款。
f04｜负责人推动立项，质控员可因关键风险否决上线，经营代表参与服务结果验收。
f05｜首期只做观测解释与灌溉建议，不自动控制泵阀；先回放历史资料，再小范围并行试点，不替换现有业务。
f10｜湿度传感器位置代表性不足，部分地块已经积水，系统仍然建议灌溉。
f11｜传感器被拔出地面后读数很低，系统误判为严重缺水。
f12｜24 个地块每天共 60 次观测，人工汇总约 90 分钟。
f13｜现场受限在终端与网络，只能用现有终端作业；断网时先存草稿并标注最后同步时间。
f14｜关键说明常留在个人便签或工作群里，事后再补录；说明不随单据交接。
f15｜发现异常时暂停该建议，交农事计划员核对后继续；错误结果不能覆盖原记录。
f20｜主流程六步；每一步的输入、输出与待办责任人要写清，退回原步骤必须留原因。
f21｜可提供五类材料：土壤湿度、作物生长期、天气、灌溉记录、地块图。
f22｜计划员可整理、校核、发起复核；不能代替质控签核，不能批准「只读观测与灌溉建议」以外的操作。
f23｜交接至少含五要素：业务编号、当前版本、处理状态、未解决事项、接手人；接手人确认才算完成，只发消息不算。
f24｜业务规则由业务负责人维护，按生效日期与适用范围选版本；冲突时附两套版本提交质控员，不自行合并、不选宽松条款。
f25｜异常先由计划员分派实际处理人，超约定时限升级到合作社负责人；跨岗必须明确下一责任人。
f30｜现用三套系统：农业物联平台、气象服务、农事表；账号权限彼此独立，没有统一的业务状态视图。
f31｜传感器埋深与校准记录不完整；地块面积单位不统一。
f32｜接口只读；系统只做观测与记录，不自动启动水泵、不自动施药。
f33｜先校验主编号、事件时间、版本字段；有歧义的记录进人工修复队列，不进自动推荐样本。
f34｜每天两次更新已授权业务状态；超过一个更新周期标记为「待刷新」。
f35｜接口中断时用带时间戳的上一份只读快照，界面显示「暂未更新」；重连后按业务编号去重补齐。快照只保证数据没丢、状态可追溯，不解决传感器代表性不足。
f40｜用水与作物安全条件必须由农业人员核实；异常读数不直接驱动任何执行动作。
f41｜只有授权岗位可查看五类资料；最终决定、对外承诺、资产变更须对应审批人本人确认，不得借用账号。
f42｜除三条硬线外还要检查约束条款；触及停止条件即暂停，由负责人复盘。
f43｜原始资料按授权范围保存；评价记录暂留 90 天，真实期限按组织规则另定。
f44｜四类强制转人工：传感器拔出误判、资料缺依据、版本冲突、关键系统不可用；须标注触发原因、接手人、确认时间。
f45｜审计保留业务编号、资料版本、事实引用、建议结果、人工改动、签核人；可重建完整六步链。
f50｜技术员按地块实际状况决策，经营方按用水成本考核；同一笔建议交接时容易互相推责。
f51｜要求逐笔采集交接等待时长与重新联系次数；不能用发送通知的数量代替实际完成量。
f52｜本次范围是观测解释与灌溉建议；不自动控制泵阀。
f53｜必须分别记录各岗位完成时间，固定分母、排除规则与统计周期；不得把同一业务拆成多次「成功」。
f54｜先关联业务编号与资料版本再查交接；争议由经营代表受理、计划员核对；未确认前不承诺赔偿或结果。
f55｜每周收集误判例子与未解决问题，由负责人确认改进责任人；先复测三条验收，再更新规则版本。
</evidence>
```

## 4. 自检提示词（生成后必跑）

生成正文后，用以下提示词做一次自查；结果与 `POST /api/harness/check` 的结论应当一致。

```text
你是合规审查员，只做检查，不改写。请对下面这段文本逐条判定，每条给出「通过 / 不通过 + 命中原文」：

H2 证据编号：出现的 fxx 是否都在 f00–f55 范围内，且真实存在于证据块；
H3 角色错配：是否出现六角色之外的人（农户、台账管理员、设备维护员、节水监管专员、运维人员、灌区管理者）；
H4 虚构实体：是否出现 E01、R01、R02 这类自造编号，或未经确认的地块名、作物名；
H5 方案越界：是否把「自动控制泵阀 / 自动灌溉 / 自动开阀」当成方案提出（否定语境如「不自动控制泵阀」不算违规）；
H6 自创数值：是否出现未经抽样的工时区间或月发生频次；
H7 边界声明：是否显式写明只读 / 不自动控制泵阀 / 观测解释与灌溉建议；
H8 数值标注：每个含数字加单位的句子，是否都带「待样本验证 / 待采集 / 待核实」。

最后只输出一行结论：PASS 或 BLOCK，并列出未通过项编号。
```

## 5. 常见误用与修正

| 误用 | 后果 | 修正 |
| --- | --- | --- |
| 把系统提示词和任务骨架合成一段 | 模型把纪律当素材，开始编造 | 严格三层分开 |
| 只给任务、不给 `<evidence>` | 模型必然编造细节 | 证据块必须每次注入 |
| 直接采信模型输出 | 编造内容进入提交稿 | 必须过 Harness |
| 用「针对某低洼地块」举例 | 生成虚构实体并被 H4 拦截 | 举例一律标为待验证假设 |
| 把估算工时写成确定值 | H8 报警，且业务上失真 | 数值后紧跟「待样本验证」 |
